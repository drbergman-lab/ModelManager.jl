Building a Simulator Backend

This is the guide for the audience ModelManager exists to serve: developers writing a Julia package that drives a particular simulator. You implement one interface — AbstractSimulator — and ModelManager provides the trial hierarchy, variations, database, runner, sensitivity analysis, and calibration on top of it.

PhysiCellModelManager.jl is the reference implementation; this page describes the contract it (and your package) fulfills.

The big picture

Arrows point from caller to callee (X ──▶ Y means "X calls Y").

You define one concrete type and implement a handful of methods on it:

  MySimulator <: AbstractSimulator

ModelManager calls your methods at the right moments during a run:

  runner                ──▶  simulationCommand(sim, spec) the command that runs one simulation
  prepareTrialHierarchy ──▶  setupSampling / setupMonad   prepare before running
  database + versioning ──▶  simulatorVersion* methods    schema + version tracking
  migration framework   ──▶  upgrade* methods             schema migrations (optional)

You call ModelManager once, at load time, to wire everything up:

  __init__ (registerSimulator!) ──▶  initializeModelManager

You supply a concrete type and a handful of methods; ModelManager calls them at the right moments. Anything you do not override falls back to a sensible default (no-op or error, depending on whether the method is optional or required).

1. Define the simulator type

using ModelManager

mutable struct MySimulator <: AbstractSimulator
    # Whatever your backend needs; ModelManager requires no fields at all.
    dir::String
    version::VersionNumber
end

2. Register your simulator in __init__

ModelManager keeps all per-project state in a ModelManagerGlobals accessed through mm_globals. One call when your package loads creates it:

function __init__()
    ModelManager.registerSimulator!(MySimulator("/path", v"0.1.0"))
end

registerSimulator! is idempotent for your own backend, so reloading the package does not wipe an open project, and it warns rather than silently taking over if another backend is already registered: one process serves one backend. The Ref behind it is internal; this call is the whole registration API.

3. Provide an initialization entry point

Expose a function your users call to open a project. Do any backend-specific validation, then delegate to initializeModelManager, which opens the database, resolves/migrates the version, parses inputs.toml, builds the schema, and launches diagnostics:

function initializeMyProject(path_to_data::AbstractString)
    # ...validate paths, set simulator-specific globals...
    return initializeModelManager(simulator(), path_to_data)
end

4. Implement the required interface

These methods have no default — ModelManager errors if they are called and not implemented. Dispatch each on your concrete type.

Running a simulation

ModelManager.simulationCommand(sim::MySimulator, spec::SimulationSpec)::Union{Nothing,Cmd}

The one thing about launching a simulation that only you know: which command runs it. Setup has already happened (see below), so everything you need is in the SimulationSpec. Return a bare Cmd — set its dir if it must run somewhere other than simulatorDir, but do not attach an environment or wrap it in a pipeline; both are rejected, for reasons the runSimulation docstring explains. Return nothing when no command can be built: that fails the one simulation without aborting the rest of the trial.

Everything else is done for you by the default runSimulation: it creates the simulation's output folder, sends stdout and stderr to output.log and output.err there, runs the command in the right directory, and — when HPC mode is on — submits it to SLURM and waits for it instead. You override runSimulation only if your simulation is not an external process at all.

Setup hooks

ModelManager.setupSampling(sim::MySimulator, S::AbstractSampling; kwargs...)::Bool
ModelManager.setupMonad(sim::MySimulator, M::AbstractMonad; kwargs...)::Bool

Called during the runner's preparation phase, before any simulation runs. setupSampling runs once per unique input-folder group (typically: compile shared custom code); setupMonad prepares each monad's varied input folders. Both return true/false for success. They accept the abstract types so they work for a bare Simulation or Monad without a wrapping object.

Simulator metadata and versioning

ModelManager.simulatorDir(sim::MySimulator)::String
ModelManager.simulatorInfo(sim::MySimulator)::String
ModelManager.simulatorVersionSchema(sim::MySimulator)::String
ModelManager.simulatorVersionIDName(sim::MySimulator)::String      # e.g. "my_version_id"
ModelManager.simulatorVersionTableName(sim::MySimulator)::String   # e.g. "my_versions"
ModelManager.resolveSimulatorVersionID(sim::MySimulator)::Int
ModelManager.currentSimulatorVersionID(sim::MySimulator)::Int

These let ModelManager build the database schema (one version table and one version-FK column per simulator) and stamp every simulation with the simulator version that produced it.

Inferring a variation's location

A user names a parameter by its path in an input file, and every variation also needs the project location that file belongs to. The explicit constructors take it first, DiscreteVariation(:config, target, values). The location-free forms leave it out, and ModelManager asks your backend:

ModelManager.inferVariationLocation(sim::MySimulator, target::XMLPath)::Symbol

Return the location symbol for target: one of the locations the project's inputs.toml declares. target.xml_path is the path as a Vector{String}. How you decide is up to you. A backend whose input files are differentiated by their root element could use that to drive the inference:

function ModelManager.inferVariationLocation(::MySimulator, target::XMLPath)
    first_element = target.xml_path[1]
    startswith(first_element, "behavior_ruleset:") && return :rulesets_collection
    first_element == "intracellulars" && return :intracellular
    return :config
end

That one method gives your users DiscreteVariation(target, values), DistributedVariation(target, distribution), UniformDistributedVariation(target, lb, ub), NormalDistributedVariation(target, mu, sigma), ElementaryVariation(target, v), LatentVariation(latent_parameters, targets, maps[, lp_names]), and the tuple forms of CoVariation, each taking a target as an XMLPath or a plain vector of strings. The hook is always handed an XMLPath. It runs when the variation is constructed, through the registered simulator, so it works as soon as your package is loaded; the mapping should need nothing but the path.

Without an implementation the location-free forms throw an error naming your backend, and the explicit forms remain. ModelManager never guesses a location.

A related point on naming: a variation's default display name is shortVariationName(sim, location, column), where column is the slash-joined path; the default returns the column unchanged. Override shortVariationName on your type to shorten it. The simulator-first forms, DiscreteVariation(sim, target, values), derive both the location and the name through the sim they are given rather than the registered one.

Database migrations

A backend that has never changed its schema implements none of these:

MethodDefaultOverride to…
dbVersionTableName"<your package, lowercased>_version"keep a table name a shipped database already uses
upgradeMilestonesVersionNumber[]declare the releases whose schema changed
upgradeToMilestonethrowsapply one declared milestone; required once upgradeMilestones is non-empty

See Database upgrades for how these are orchestrated by upgradePackage. Migrations target the version of your package loaded in the session, read from the package defining your simulator type — the same package identity that gives dbVersionTableName its default.

6. Reach for ModelManager's own helpers

Two your backend will want rather than reimplement:

  • variationFilePath(location, M) — the path createXMLFile writes a monad's variation file to. Ask for it instead of rebuilding the <location>_variation_<id>.xml convention; the path is computed from the monad, so it is available before the file exists.
  • quietRun(cmd) — run a command with stdout and stderr sent to devnull, for probing that a simulator executable is present without printing its output.

Boundary rules

  • ModelManager does not resolve a variation target to a project location. The explicit constructors take location first; the location-free ones ask your backend through inferVariationLocation and throw until you implement it. Implement the one hook rather than adding location-free constructors of your own. See Variations.
  • No simulator specifics leak into ModelManager. If you find yourself wanting ModelManager to know something about your simulator, that knowledge belongs behind one of these interface methods — add or override a hook rather than special-casing the core.

For the exact signatures and contracts of every method, see the AbstractSimulator interface API reference.
